1. Übersicht

Der SimpleAdmin ist ein Monitoring-Tool, das System-Metriken überwacht und statische HTML-Seiten für LoadBalancer (NetScaler) und Monitoring-Systeme (PRTG) generiert.

Konfigurationsdatei: SimpleAdmin/config/config.json
JSON Schema: SimpleAdmin/config/config.schema.json

Hauptfunktionen

  • System-Metriken: CPU, Memory, Disk-Überwachung
  • PRTG Integration: Generiert HTML-Seiten für PRTG-Sensoren
  • NetScaler Integration: Generiert HTML-Seiten für LoadBalancer Health Checks
  • Verlaufsdaten: Speichert historische Metrik-Daten
  • OK-Marker: HTML-Kommentar zur automatischen Status-Erkennung

Deployment-Modell

SimpleAdmin läuft als einmaliger Task, nicht als kontinuierlicher Hintergrundprozess.

SimpleAdmin wird typischerweise per Cronjob oder Docker-Trigger aufgerufen, führt seine Arbeit aus und beendet sich dann:

  1. Metriken sammeln: Liest aktuelle CPU, Memory, Disk-Werte
  2. Status berechnen: Vergleicht mit Schwellwerten und bestimmt Service-Status
  3. Verlauf aktualisieren: Speichert Metrik-Historie in JSON-Dateien
  4. HTML generieren: Erstellt/aktualisiert alle HTML-Seiten im wwwroot-Verzeichnis
  5. Beenden: Programm terminiert

Wichtige Konsequenz: Parameter wie intervalSeconds und timeoutMs in den NetScaler Health Checks sind reine Dokumentation - sie beschreiben, wie oft der LoadBalancer die generierten HTML-Seiten abrufen soll, werden aber nicht von SimpleAdmin selbst verwendet.

Typische Deployment-Szenarien

Szenario Beschreibung Beispiel
Docker Post-Build Wird nach jedem Build automatisch ausgeführt docker exec simpleadmin-dev dotnet SimpleAdmin.dll
Cronjob Läuft alle X Minuten auf dem Server */5 * * * * /usr/local/bin/simpleadmin
Systemd Timer Linux Systemd-Timer für regelmäßige Ausführung systemctl start simpleadmin.service
Kubernetes CronJob Kubernetes CronJob für Container-Umgebungen schedule: "*/5 * * * *"

Die Hauptkonfigurationsdatei enthält drei Hauptbereiche:

{
  "history": { ... },    // Verlaufsdaten-Konfiguration

}

2.2 history - Verlaufsdaten und Status-Glättung

config.history

Konfiguriert die Speicherung von historischen Metrik-Daten und die Status-Glättung zur Vermeidung von Alert-Fatigue.

Knoten: maxEntries

config.history.maxEntries
Eigenschaft Wert
Typ integer
Pflicht Optional
Default 500
Beschreibung Maximale Anzahl der Verlaufseinträge pro Service
Empfehlung: Bei häufigen Updates (z.B. alle 30 Sekunden) entsprechen 500 Einträge etwa 4 Stunden Verlauf.

Knoten: minConsecutiveChecks

config.history.minConsecutiveChecks
Eigenschaft Wert
Typ integer
Pflicht Optional
Default 5
Beschreibung Mindestanzahl aufeinanderfolgender Messungen mit gleichem Status, bevor ein Status-Wechsel bestätigt wird
Status-Glättung: Diese Einstellung verhindert "Alert Fatigue" durch kurzfristige CPU-/Memory-Spitzen. Ein Status-Wechsel (z.B. von "OK" auf "Warning") wird erst bestätigt, wenn alle letzten N Messungen den gleichen Status zeigen.
Durchschnittswert: Auf der Detailseite wird der Durchschnittswert der letzten N Messungen angezeigt, wobei N der Wert von minConsecutiveChecks ist. Dies ermöglicht eine stabilere Einschätzung der Systemlast.
Beispiel Status-Glättung
Konfiguration: minConsecutiveChecks: 5, CPU Warning: 70%, Critical: 85%

Historie der letzten 5 CPU-Messungen:
  [95%, 92%, 88%, 65%, 70%]  →  Status: [Crit, Crit, Crit, Ok, Ok]

Ergebnis: Nur 3/5 Messungen sind "Critical" → Status wird NICHT auf Critical gesetzt
          Der stabilste Status (häufigster) wird verwendet → "Critical" (3x)

Nächste Messung mit [92%, 88%, 65%, 70%, 68%]:
  Status: [Crit, Crit, Ok, Ok, Ok]
  Ergebnis: 3/5 sind "Ok" → Status bleibt bei "Ok"
{
  "history": {
    "maxEntries": 1000,           // Speichert die letzten 1000 Messungen
    "minConsecutiveChecks": 5     // 5 aufeinanderfolgende Messungen für Status-Bestätigung
  }
}

2.3 output - HTML-Ausgabe

config.output

Konfiguriert Einstellungen für die generierten HTML-Seiten.

Knoten: okMarker

config.output.okMarker
Eigenschaft Wert
Typ string
Pflicht Optional
Default "##OK##"
Beschreibung Text-Marker als HTML-Kommentar für gesunde Services

Dieser Marker wird als HTML-Kommentar <!-- Status: ##OK## --> in die HTML-Seite eingefügt, wenn der Service gesund ist. LoadBalancer und PRTG können im Quellcode nach diesem Text suchen.

  }
}

3. Monitoring-Typen im Detail

3.1 PRTG Monitoring

PRTG-Monitoring überwacht System-Metriken (CPU, Memory, Disk) und generiert HTML-Seiten, die PRTG über HTTP-Advanced-Sensoren abrufen kann.

3.1.1 CPU-Überwachung

config.servers[].serviceTypes[].prtg.checks[] (metric: "cpu")

Überwacht die CPU-Auslastung des Systems in Prozent.

Parameter
Parameter Typ Pflicht Beschreibung
metric string Ja Muss "cpu" sein
displayName string Ja Anzeigename in HTML-Ausgabe
threshold object Ja Schwellwert-Konfiguration
Threshold-Parameter
Parameter Typ Beschreibung
warning number Warnschwelle in Prozent (z.B. 70)
critical number Kritische Schwelle in Prozent (z.B. 85)
operator string Vergleichsoperator: ">" (größer als)
Beispiel
{
  "metric": "cpu",
  "displayName": "CPU Usage",
  "threshold": {
    "warning": 70,      // Warnung bei > 70%
    "critical": 85,     // Kritisch bei > 85%
    "operator": ">"
  }
}
Interpretation
  • OK: CPU-Auslastung ≤ 70%
  • Warning: CPU-Auslastung > 70% und ≤ 85%
  • Critical: CPU-Auslastung > 85%

3.1.2 Memory-Überwachung

config.servers[].serviceTypes[].prtg.checks[] (metric: "memory")

Parameter

Beispiel
{

  "displayName": "Memory Usage",

  • Critical: Memory-Auslastung > 90%

3.1.3 Disk-Überwachung (Freier Speicherplatz)

config.servers[].serviceTypes[].prtg.checks[] (metric: "disk")

Überwacht den freien Speicherplatz eines Laufwerks in Prozent.

Wichtig: Bei Disk-Überwachung wird der freie Speicherplatz gemessen, nicht die Auslastung! Der Operator ist daher "<=" (kleiner oder gleich).
Parameter
Parameter Typ Pflicht Beschreibung
metric string Ja Muss "disk" sein
displayName string Ja Anzeigename in HTML-Ausgabe
target string Ja Laufwerk/Partition (z.B. "/", "C:", "/data")
threshold object Ja Schwellwert-Konfiguration
Threshold-Parameter (speziell für Disk)
Parameter Typ Beschreibung
warning number Warnschwelle für freien Speicher in Prozent (z.B. 20)
critical number Kritische Schwelle für freien Speicher in Prozent (z.B. 10)
operator string Vergleichsoperator: "<=" (kleiner oder gleich)
Beispiel

  "displayName": "Disk Free Space",
  "target": "/",          // Root-Partition unter Linux
  "threshold": {
    "warning": 20,        // Warnung wenn ≤ 20% frei
    "critical": 10,       // Kritisch wenn ≤ 10% frei
    "operator": "<="
  }
}

  • OK: Freier Speicher > 20%
  • Warning: Freier Speicher ≤ 20% und > 10%
  • Critical: Freier Speicher ≤ 10%
Plattform-spezifische Targets
Betriebssystem Beispiel-Targets
Linux "/", "/data", "/var"
Windows "C:", "D:"
macOS "/", "/Volumes/Data"

3.2 NetScaler Health Checks

NetScaler Health Checks führen HTTP-Requests aus und validieren die Response. Sie können APIs, Webseiten oder andere HTTP-Endpunkte überwachen.

Wichtig: SimpleAdmin läuft als einmaliger Task (z.B. über Docker exec oder Cronjob). Die Parameter intervalSeconds und timeoutMs sind reine Dokumentation für die LoadBalancer-Konfiguration und werden NICHT von SimpleAdmin verwendet. Sie dienen als Empfehlung, wie oft der LoadBalancer die generierten HTML-Seiten abrufen soll.

3.2.1 Einfache HTTP Checks

Prüft nur den HTTP-Statuscode.

Parameter
Parameter Typ Pflicht Beschreibung
name string Ja Eindeutiger Name des Health Checks
method string Ja HTTP-Methode: GET, POST, HEAD, PUT, DELETE
path string Ja URL-Pfad (relativ zu baseUrl oder absolute URL)
expected object Ja Erwartete Response-Kriterien
intervalSeconds integer Ja Dokumentation: Empfohlenes Prüfintervall für LoadBalancer (wird NICHT von SimpleAdmin genutzt)
timeoutMs integer Ja Dokumentation: Empfohlener Timeout für LoadBalancer (wird NICHT von SimpleAdmin genutzt)
Beispiel
{
  "name": "basic-health-check",
  "method": "GET",
  "path": "/health",
  "expected": {
    "statusCodes": [200]    // Erwartet HTTP 200
  },
  "intervalSeconds": 30,    // Prüft alle 30 Sekunden
  "timeoutMs": 5000         // Timeout nach 5 Sekunden
}

3.2.2 Erweiterte Checks

Prüft Statuscode, Body-Inhalt und HTTP-Header.

Body Contains Check

Sucht nach bestimmten Texten im Response-Body.

{
  "name": "api-health-with-body-check",
  "method": "GET",
  "path": "/api/v1/health",
  "expected": {
    "statusCodes": [200],
    "bodyContains": ["healthy", "ok"]  // Body muss "healthy" ODER "ok" enthalten
  },
  "intervalSeconds": 30,
  "timeoutMs": 5000
}
Header Validation

Validiert HTTP-Response-Header.

{
  "name": "api-with-header-check",
  "method": "GET",
  "path": "/api/v1/status",
  "expected": {
    "statusCodes": [200],
    "headers": {
      "Content-Type": "application/json",    // Exakte Übereinstimmung erforderlich
      "X-API-Version": "2.0"
    }
  },
  "intervalSeconds": 45,
  "timeoutMs": 8000
}
POST Request mit Payload

Sendet JSON-Daten im Request-Body.

{
  "name": "database-connection-check",
  "method": "POST",
  "path": "/api/v1/healthcheck/database",
  "payload": "{\"check\": \"connection\", \"timeout\": 5000}",
  "expected": {
    "statusCodes": [200],
    "bodyContains": ["connected", "healthy"]
  },
  "intervalSeconds": 60,
  "timeoutMs": 10000
}

3.2.3 JSON Path Validierung

Validiert spezifische Werte in JSON-Responses.

JSON Path Syntax
Parameter Typ Beschreibung
path string JSON-Path-Ausdruck (z.B. $.status, $.data.health)
operator string Vergleichsoperator: ==, !=, <, >, <=, >=
value any Erwarteter Wert (string, number, boolean)
Beispiel: String-Validierung
// Erwartete JSON-Response:
// { "status": "healthy", "version": "1.0" }

{
  "name": "api-status-check",
  "method": "GET",
  "path": "/api/status",
  "expected": {
    "statusCodes": [200],
    "jsonPath": [
      {
        "path": "$.status",
        "operator": "==",
        "value": "healthy"    // $.status muss "healthy" sein
      }
    ]
  },
  "intervalSeconds": 30,
  "timeoutMs": 5000
}
Beispiel: Numerische Validierung
// Erwartete JSON-Response:
// { "status": "healthy", "responseTime": 450 }

{
  "name": "performance-check",
  "method": "GET",
  "path": "/api/health",
  "expected": {
    "statusCodes": [200],
    "jsonPath": [
      {
        "path": "$.status",
        "operator": "==",
        "value": "healthy"
      },
      {
        "path": "$.responseTime",
        "operator": "<",
        "value": 1000        // Response-Zeit muss < 1000ms sein
      }
    ]
  },
  "intervalSeconds": 30,
  "timeoutMs": 5000
}
Beispiel: Verschachtelte JSON-Pfade
// Erwartete JSON-Response:
// {
//   "data": {
//     "database": {
//       "status": "connected",
//       "connections": 42
//     }
//   }
// }

{
  "name": "database-deep-check",
  "method": "GET",
  "path": "/api/health/database",
  "expected": {
    "statusCodes": [200],
    "jsonPath": [
      {
        "path": "$.data.database.status",
        "operator": "==",
        "value": "connected"
      },
      {
        "path": "$.data.database.connections",
        "operator": ">",
        "value": 0           // Mindestens 1 Connection
      }
    ]
  },
  "intervalSeconds": 60,
  "timeoutMs": 8000
}
Externe URLs

Wenn path mit http:// oder https:// beginnt, wird es als absolute URL verwendet:

{
  "name": "external-service-check",
  "method": "GET",
  "path": "https://api.external.com/health",  // Absolute URL
  "expected": {
    "statusCodes": [200, 201]
  },
  "intervalSeconds": 60,
  "timeoutMs": 10000
}
Hinweis: Bei absoluten URLs wird baseUrl ignoriert.

4. Operator-Referenz - Alle verfügbaren Operatoren

SimpleAdmin verwendet Vergleichsoperatoren an zwei Stellen: bei PRTG-Threshold-Prüfungen und bei JSON-Path-Validierungen. Diese Sektion listet alle verfügbaren Operatoren auf.

4.1 PRTG Threshold Operatoren

Verwendet in: threshold.operator bei PRTG-Checks

Operator Bedeutung Verwendung Beispiel
> Größer als Alarm wenn Wert ÜBER dem Schwellwert liegt CPU > 85% → Warning bei 86%
>= Größer gleich Alarm wenn Wert ÜBER ODER GLEICH dem Schwellwert liegt CPU >= 85% → Warning bei 85%
< Kleiner als Alarm wenn Wert UNTER dem Schwellwert liegt Disk Free < 10% → Critical bei 9%
<= Kleiner gleich Alarm wenn Wert UNTER ODER GLEICH dem Schwellwert liegt Disk Free <= 10% → Critical bei 10%
== Gleich Alarm wenn Wert EXAKT dem Schwellwert entspricht ErrorCount == 0 → Warning bei genau 0
!= Ungleich Alarm wenn Wert NICHT dem Schwellwert entspricht Status != 1 → Warning wenn nicht 1

Typische Verwendung nach Metrik

Metrik Empfohlener Operator Begründung
cpu > Alarm bei HOHER Auslastung (über 70%, über 85%)
memory > Alarm bei HOHER Auslastung (über 80%, über 90%)
disk <= Alarm bei WENIG freiem Speicher (≤20%, ≤10%)
Wichtig bei Disk-Monitoring: Der Wert ist freier Speicher, nicht Auslastung! Daher wird <= verwendet: Alarm wenn zu WENIG frei ist.

Beispiele PRTG Threshold

{
  "metric": "cpu",
  "displayName": "CPU Usage",
  "threshold": {
    "warning": 70,       // Warnung bei > 70%
    "critical": 85,      // Kritisch bei > 85%
    "operator": ">"      // Alarm wenn ÜBER dem Wert
  }
}
{
  "metric": "disk",
  "displayName": "Disk Free Space",
  "target": "/",
  "threshold": {
    "warning": 20,       // Warnung bei <= 20% frei
    "critical": 10,      // Kritisch bei <= 10% frei
    "operator": "<="     // Alarm wenn UNTER ODER GLEICH dem Wert
  }
}

4.2 JSON Path Operatoren

Verwendet in: expected.jsonPath[].operator bei NetScaler Health Checks

Operator Bedeutung Typ-Unterstützung Beispiel
== Gleich (Exakte Übereinstimmung) String, Number, Boolean $.status == "healthy"
!= Ungleich String, Number, Boolean $.errors != 0
> Größer als Nur Number $.connections > 0
>= Größer gleich Nur Number $.uptime >= 60
< Kleiner als Nur Number $.responseTime < 1000
<= Kleiner gleich Nur Number $.errorRate <= 0.01
JSON Path ist Case-Sensitive: $.Status ist nicht das gleiche wie $.status

Beispiele nach Datentyp

String-Vergleich
// JSON Response: { "status": "healthy", "version": "2.0" }

{
  "path": "$.status",
  "operator": "==",         // Nur == oder != für Strings
  "value": "healthy"        // String-Wert (mit Anführungszeichen in JSON)
}
Number-Vergleich
// JSON Response: { "responseTime": 450, "connections": 42 }

{
  "path": "$.responseTime",
  "operator": "<",          // Alle 6 Operatoren verfügbar für Numbers
  "value": 1000            // Number-Wert (OHNE Anführungszeichen in JSON)
},
{
  "path": "$.connections",
  "operator": ">",
  "value": 0               // Mindestens 1 Connection
}
Boolean-Vergleich
// JSON Response: { "isHealthy": true, "maintenance": false }

{
  "path": "$.isHealthy",
  "operator": "==",         // Nur == oder != für Boolean
  "value": true            // Boolean-Wert (OHNE Anführungszeichen)
},
{
  "path": "$.maintenance",
  "operator": "!=",
  "value": true            // Maintenance darf NICHT aktiv sein
}
Verschachtelte Pfade
// JSON Response:
// {
//   "data": {
//     "database": {
//       "status": "connected",
//       "latency": 12.5,
//       "poolSize": 20
//     }
//   }
// }

{
  "path": "$.data.database.status",
  "operator": "==",
  "value": "connected"
},
{
  "path": "$.data.database.latency",
  "operator": "<",
  "value": 50              // Latenz muss unter 50ms sein
},
{
  "path": "$.data.database.poolSize",
  "operator": ">=",
  "value": 10              // Mindestens 10 Connections im Pool
}

Vollständiges Health Check Beispiel

{
  "name": "comprehensive-api-check",
  "method": "GET",
  "path": "/api/v1/health",
  "expected": {
    "statusCodes": [200],
    "jsonPath": [
      {
        "path": "$.status",
        "operator": "==",      // String: Exakte Übereinstimmung
        "value": "healthy"
      },
      {
        "path": "$.services.database",
        "operator": "==",      // String: Exakte Übereinstimmung
        "value": "connected"
      },
      {
        "path": "$.metrics.responseTime",
        "operator": "<",       // Number: Muss kleiner sein
        "value": 500
      },
      {
        "path": "$.metrics.activeUsers",
        "operator": ">",       // Number: Muss größer sein
        "value": 0
      },
      {
        "path": "$.maintenanceMode",
        "operator": "!=",      // Boolean: Darf NICHT true sein
        "value": true
      }
    ]
  },
  "intervalSeconds": 30,
  "timeoutMs": 5000
}
Häufiger Fehler: Verwende "value": 1000 (Number) statt "value": "1000" (String) bei numerischen Vergleichen!

5. OK-Marker

Der OK-Marker ist ein HTML-Kommentar, der automatisch in Endpoint-Seiten eingefügt wird. LoadBalancer und PRTG können nach diesem Text suchen, um den Service-Status zu ermitteln.

Unterschiedliches Verhalten für PRTG und NetScaler

Wichtig: Der OK-Marker verhält sich unterschiedlich je nach Endpoint-Typ, um eine differenzierte Alarmierung zu ermöglichen.
Status PRTG (/monitor/) NetScaler (/loadbalancer/)
Healthy (OK) OK-Marker vorhanden ✓ OK-Marker vorhanden ✓
Degraded (Warning) OK-Marker NICHT vorhanden ✗ OK-Marker vorhanden ✓
Unhealthy (Critical) OK-Marker NICHT vorhanden ✗ OK-Marker NICHT vorhanden ✗
Unknown OK-Marker NICHT vorhanden ✗ OK-Marker NICHT vorhanden ✗
Begründung:
  • PRTG: Soll bereits bei Warning alarmieren → OK-Marker fehlt bei Degraded
  • NetScaler: Server soll erst bei Critical aus dem LoadBalancer genommen werden → OK-Marker bleibt bei Degraded

Konfiguration

{
  "output": {
    "okMarker": "##OK##"  // Anpassbar an LoadBalancer-Anforderungen
  }
}

LoadBalancer-Konfiguration

NetScaler

Der NetScaler prüft /admin/*/loadbalancer/ - Server bleibt im Pool bei Warning.

Monitor Type: HTTP
URL: /admin/api-gateway/loadbalancer/
Response Code: 200
Response Contains: ##OK##

PRTG

PRTG prüft /admin/*/monitor/ - Alarm wird bei Warning ausgelöst.

Sensor Type: HTTP Advanced
URL: http://your-server.com/admin/api-gateway/monitor/
Expected HTTP Status: 200

7. Windows Service-Überwachung

SimpleAdmin überwacht Windows-Dienste (Services) über sc.exe und meldet Probleme, wenn ein überwachter Dienst nicht läuft oder nicht gefunden wird. Welche Dienste überwacht werden, steuern die Startart-Filter (Automatisch / Manuell) pro Eintrag.

Nur Windows: Die Service-Überwachung ist ausschließlich auf Windows verfügbar. Auf Linux und macOS wird der Check übersprungen und liefert leere Ergebnisse.

Aktivierung

  1. Globalen Feature-Toggle setzen: features.services.enabled: true
  2. Pro-Server-Toggle setzen: servers[].checks.services.enabled: true
  3. Dienste in servers[].checks.services.checks[] konfigurieren.

Globales Feature-Toggle

{
  "features": {
    "services": {
      "enabled": true
    }
  }
}

Pro-Server-Konfiguration

{
  "checks": {
    "services": {
      "enabled": true,
      "checks": [
        {
          "name": "SQLWriter",
          "displayName": "SQL Server VSS Writer",
          "monitorAutomatic": true,
          "monitorManual": false
        },
        {
          "name": "W3SVC",
          "displayName": "World Wide Web Publishing Service",
          "monitorAutomatic": true,
          "monitorManual": true
        }
      ]
    }
  }
}

Vor der Statusprüfung liest SimpleAdmin den in Windows konfigurierten Starttyp des Dienstes (sc.exe qc) und entscheidet anhand der Konfiguration, ob der Dienst überwacht wird:

Wildcard-Unterstützung

Der Dienstname unterstützt die Wildcards * (beliebig viele Zeichen) und ? (genau ein Zeichen). Bei einem Wildcard-Muster werden zur Laufzeit alle passenden Dienste via sc.exe query type= all state= all ermittelt, dann nach Starttyp gefiltert und einzeln überwacht. 

{
  "checks": {
    "services": {
      "enabled": true,
      "checks": [
        { "name": "SQL*",      "displayName": "SQL-Dienste",  "monitorAutomatic": true },
        { "name": "*BizTalk*", "displayName": "BizTalk",      "monitorAutomatic": true }
      ]
    }
  }
}
  • SQL* → findet z.B. SQLWriter, SQLBrowser, MSSQLSERVER
  • *BizTalk* → findet alle Dienste, die „BizTalk" im Namen enthalten
  • Bei displayName: "SQL-Dienste" erscheint jeder gefundene Dienst als SQL-Dienste / SQLWriter in der UI
  • Treffer, deren Starttyp nicht dem Filter entspricht, werden still übersprungen

Kein Namens-Treffer: Wenn das Muster keinen Dienst findet (unabhängig vom Starttyp), wird ein Critical-Problem mit der ID service_{muster}_nomatch erzeugt (z.B. service_sql__nomatch für Muster SQL*).

Statuslogik

  • Dienst läuft (Running) → Healthy
  • Dienst hat Starttyp Disabled → übersprungen (kein Eintrag, kein Problem)
  • Dienst hat Starttyp, der nicht überwacht wird → übersprungen (kein Eintrag, kein Problem)
  • Dienst gestoppt (Stopped) → Critical — Meldung enthält die Startart, z.B. „Service 'SQLWriter' ist nicht gestartet (Startart: Automatisch)"
  • Dienst nicht gefunden (NotFound) → Critical
  • Wildcard ohne Namens-Treffer → Critical (Problem-ID: service_{muster}_nomatch)
Startart in Meldungen: Wenn der Starttyp eines gestoppten oder nicht gefundenen Dienstes bekannt ist, wird er automatisch in die Fehlermeldung und in die Detailansicht aufgenommen (Startart: Automatisch oder Startart: Manuell). So ist auf einen Blick erkennbar, ob ein eigentlich automatisch startender Dienst ausgefallen ist.

Problem-IDs sind deterministisch und ermöglichen gezielte Quittierungen: service_{name}_stopped für gestoppte Dienste (z.B. service_com.docker.service_stopped), service_{muster}_nomatch für Wildcard ohne Treffer.

8. Windows EventLog-Überwachung

SimpleAdmin kann Windows Event Logs (z.B. Application, System) auf Fehler und kritische Ereignisse überwachen. Die Abfrage erfolgt via PowerShell Get-WinEvent mit Level-Filter innerhalb des FilterHashtable.

Nur Windows: EventLog-Prüfungen sind ausschließlich auf Windows verfügbar. Auf Linux/macOS wird die Prüfung übersprungen; kein Fehler, kein Ergebnis.

Aktivierung (zweistufig)

Beide Schritte sind erforderlich:

  1. Globales Feature-Toggle in features.eventLog.enabled: true setzen. Dort lassen sich auch die globalen Standardwerte (Zeitfenster, Schwellwerte, Level) konfigurieren.
  2. Pro-Server-Check in servers[].checks.eventLog.enabled: true setzen.

Globale Feature-Konfiguration

{
  "features": {
    "eventLog": {
      "enabled": true,
      "defaults": {
        "timeWindowMinutes": 60,
        "warningCount": 5,
        "criticalCount": 20,
        "levels": ["Critical", "Error"]
      }
    }
  }
}

Pro-Server-Konfiguration

Wenn logs leer ist, werden automatisch Application und System geprüft (Standardverhalten). Individuelle Logs können mit optionalen Schwellwert-Overrides und Quell-Filtern angegeben werden: 

{
  "checks": {
    "eventLog": {
      "enabled": true,
      "logs": [
        {
          "name": "Application",
          "timeWindowMinutes": 30,
          "levels": ["Critical", "Error"],
          "warningCount": 3,
          "criticalCount": 10,
          "includeSources": ["MSSQLSERVER"],
          "excludeSources": ["SecurityCenter"]
        },
        {
          "name": "System"
        }
      ]
    }
  }
}

Statuslogik

Der Status wird pro Log berechnet; der schlechteste Status über alle Logs wird gemeldet:

  • Ereignisanzahl ≥ criticalCount → Critical
  • Ereignisanzahl ≥ warningCount → Warning
  • Ereignisanzahl < warningCount → Healthy (kein Problem)

Bei Warning oder Critical erzeugt ProblemDerivationService automatisch ein aktives Problem mit der deterministischen ID eventlog_errors_critical bzw. eventlog_errors_warning. Diese ID ermöglicht gezielte Quittierungen (Acknowledge).

Sofortige Auslösung: EventLog-Probleme unterliegen nicht dem Status-Smoothing (minConsecutiveChecks). Sie werden beim ersten Überschreiten der Schwelle sofort gemeldet — im Gegensatz zu Metrik-Problemen (CPU, Disk), die N aufeinanderfolgende Checks benötigen.

Anzeige

  • Statische HTML-Detailseite (<server>.<service>.html): Abschnitt „Event Log" mit Ereignistabelle (Zeitstempel, Level, Quelle, ID, Meldung).
  • WebUI-Detailseite (Status → [Server]): Event-Log-Karte mit farbcodierten Level-Badges und Ereignisanzahl im Badge.
  • Aktive Probleme: EventLog-Problem erscheint in der Problemliste und kann über die WebUI quittiert werden.

Es werden pro Log maximal 20 Ereignisse und insgesamt maximal 50 Ereignisse im Snapshot gespeichert. Die Gesamtanzahl (EventCount) spiegelt alle gefundenen Events wider (auch über 50).

Troubleshooting: Keine Events trotz aktiviertem Check

  • Prüfe, ob beide Feature-Toggles aktiv sind (global und pro Server).
  • Stelle sicher, dass SimpleAdmin auf Windows läuft — auf Linux/macOS wird der Check übersprungen.
  • Prüfe das Zeitfenster (timeWindowMinutes) — bei kurzen Fenstern können keine Errors vorhanden sein.
  • Überprüfe den Level-Filter: Standard ist nur Critical (1) und Error (2), keine Warnings.
  • Starte SimpleAdmin mit erhöhten Rechten, falls Security-Logs abgefragt werden sollen (erfordert Administratorrechte).

9. SQL Query Checks

9.1 Zweck

SQL Query Checks ermöglichen die Validierung von Datenbankabfrage-Ergebnissen direkt aus der SimpleAdmin-Konfiguration heraus. Pro Server können beliebig viele Verbindungen (checks) mit je mehreren Abfragen (queries) definiert werden. Geprüft werden sowohl die Anzahl der zurückgegebenen Zeilen (RowCount) als auch konkrete Spaltenwerte (ColumnAssertions).

ColumnAssertions werden gegen alle Zeilen des Ergebnis-Sets ausgewertet. Eine Assertion gilt als bestanden, wenn sie für jede einzelne Zeile erfüllt ist. Schlägt mindestens eine Zeile fehl, wird ein Critical-Problem ausgelöst — mit einer Zusammenfassung wie „2/3 rows failed" und den konkreten Fehlerwerten pro Zeile.

Typische Anwendungsfälle sind: offene Verarbeitungsjobs in einer BizTalk-Datenbank, veraltete Synchronisations-Zeitstempel, unerwartete Fehlerzähler in Applikationstabellen oder fehlende Pflichtdatensätze in Stammdaten.

9.2 Konfiguration

Globales Feature-Toggle

SQL Query Checks werden über features.sqlQueries.enabled global aktiviert. Der optionale defaultTimeoutSeconds-Wert gilt für alle Checks, die keinen eigenen Timeout definieren: 

{
  "features": {
    "sqlQueries": {
      "enabled": true,
      "defaultTimeoutSeconds": 30
    }
  }
}

Pro-Server-Konfiguration

Innerhalb des jeweiligen Server-Eintrags wird sqlQueries als Array von Verbindungs-Checks angelegt. Jeder Check erhält einen eindeutigen name (Slug, wird für Problem-IDs verwendet), eine optionale description, eine connectionString sowie ein queries-Array: 

{
  "sqlQueries": {
    "enabled": true,
    "checks": [
      {
        "name": "biztalk-db",
        "description": "BizTalk Datenbank",
        "connectionString": "enc:v1:abc123....xyz789",
        "timeoutSeconds": 30,
        "queries": [
          {
            "name": "Offene Jobs",
            "sql": "SELECT COUNT(*) AS Cnt FROM dbo.bts_MessageBox_Jobs WHERE nStatus = 0",
            "rowCount": { "expectedCount": 0, "operator": "==" },
            "columnAssertions": [
              {
                "name": "Status-Spalte",
                "column": "Cnt",
                "expectedValue": "0",
                "operator": "==",
                "valueType": "Integer"
              }
            ]
          }
        ]
      }
    ]
  }
}

9.3 Konfiguration über die WebUI

SQL Query Checks lassen sich vollständig über die grafische Oberfläche unter Server → Bearbeiten → SQL Query Checks konfigurieren, ohne die config.json direkt bearbeiten zu müssen.

  1. In der WebUI unter Einstellungen → Features die Option SQL Queries global aktivieren.
  2. Den Server unter Server → Bearbeiten öffnen.
  3. Im Abschnitt SQL Query Checks den Toggle Aktiviert einschalten.
  4. Mit Check-Gruppe hinzufügen eine neue Verbindung anlegen: Name (Slug, z.B. biztalk-db), Beschreibung (optional) und Connection-String eingeben.
  5. Mit Abfrage hinzufügen eine oder mehrere SQL-Abfragen definieren. Pro Abfrage können RowCount-Assertions und ColumnAssertions ergänzt werden.
  6. Mit Verbindung testen kann der Connection-String direkt aus der WebUI geprüft werden (liefert Serverversion bei Erfolg, Fehlermeldung bei Fehler). Mit Abfrage testen lassen sich die ersten 50 Zeilen des Ergebnisses in einer Vorschau anzeigen.
  7. Änderungen speichern speichert die Änderungen in der Laufzeit-Konfiguration (in-memory). Der Connection-String wird dabei automatisch verschlüsselt (enc:v1:…). Dauerhaft gespeichert wird erst über Import/Export → Konfiguration speichern.
Verbindungs- und Abfrage-Test: Der Verbindung testen-Button ruft POST /api/sqlquerytest/connection auf. Der Abfrage testen-Button ruft POST /api/sqlquerytest/query auf und gibt die ersten 50 Ergebniszeilen als Vorschautabelle aus — nützlich zur Validierung von SQL-Syntax und Spaltennamen vor dem produktiven Einsatz.

9.4 Unterstützte Datentypen

Der valueType einer ColumnAssertion bestimmt, wie expectedValue interpretiert und verglichen wird:

String

Zeichenketten-Vergleich, Groß-/Kleinschreibung wird ignoriert (case-insensitive). Unterstützte Operatoren: == und !=. 

{
  "column": "Status",
  "expectedValue": "active",
  "operator": "==",
  "valueType": "String"
}

Integer

Der Spaltenwert wird als long geparst. Unterstützte Operatoren: ==, !=, >, >=, <, <=. 

{
  "column": "Cnt",
  "expectedValue": "0",
  "operator": "==",
  "valueType": "Integer"
}

DateTime

Der Spaltenwert wird als DateTime interpretiert. expectedValue akzeptiert sowohl ISO 8601-Zeitstempel als auch relative Token:

TokenBedeutung
nowAktueller Zeitpunkt
todayHeutiger Tag um 00:00:00 Uhr
now-30mAktueller Zeitpunkt minus 30 Minuten
now-1hAktueller Zeitpunkt minus 1 Stunde
now-1dAktueller Zeitpunkt minus 1 Tag
now+1hAktueller Zeitpunkt plus 1 Stunde (Zukunft)

Unterstützte Operatoren: ==, !=, >, >=, <, <=.

{
  "column": "LetzteAktualisierung",
  "expectedValue": "now-1h",
  "operator": ">=",
  "valueType": "DateTime"
}

Im obigen Beispiel wird geprüft, ob LetzteAktualisierung nicht älter als eine Stunde ist — ein typischer Freshness-Check für Synchronisationsjobs.

9.5 Alert-Verhalten

SQL Query Checks lösen immer Critical aus — es gibt keine Warning-Stufe. Ein Critical-Problem wird erzeugt, wenn einer der folgenden Fälle eintritt:

  • Verbindungsfehler: Die Datenbankverbindung kann nicht hergestellt werden (falsche Credentials, Server nicht erreichbar, Timeout).
  • Query-Fehler: Die SQL-Abfrage schlägt fehl (Syntaxfehler, fehlende Tabelle, fehlende Berechtigung).
  • RowCount-Mismatch: Die Anzahl der zurückgegebenen Zeilen erfüllt den definierten Operator-Vergleich nicht.
  • ColumnAssertion-Fehler: Mindestens eine Zeile im Ergebnis-Set erfüllt den Vergleich mit expectedValue nicht. Alle Zeilen werden geprüft — ein Fehlschlag in einer Zeile bricht die Auswertung der übrigen Zeilen und Assertions nicht ab.
Sofortige Auslösung: SQL Query Check-Probleme unterliegen nicht dem Status-Smoothing (minConsecutiveChecks). Ein Fehlschlag wird beim ersten Auftreten sofort als Critical gemeldet — analog zum EventLog-Checker.

Problem-IDs sind deterministisch aufgebaut: sqlquery_{checkId}_{queryName} (normalisiert auf Kleinbuchstaben, Leerzeichen durch Unterstriche ersetzt). Dadurch können SQL Query Check-Probleme gezielt über die Acknowledge-Funktion quittiert werden.

Verschlüsselung von Connection-Strings: Connection-Strings werden beim Speichern über die WebUI automatisch mit AES-256-CBC / PBKDF2-HMACSHA256 verschlüsselt. Der verschlüsselte Wert beginnt mit dem Präfix enc:v1: gefolgt von Salt, IV und Chiffrat (je Base64, durch Punkte getrennt). Klartextwerte in bestehenden Konfigurationen werden beim nächsten Speichervorgang automatisch migriert.

Der Master-Key wird nicht in config.json gespeichert — er muss in appsettings.json (oder per Umgebungsvariable Encryption__ConnectionStringKey) beider Instanzen (Worker und WebUI) identisch hinterlegt sein: 
{
  "Encryption": {
    "ConnectionStringKey": "<base64-kodierter 32-Byte-Zufallsschlüssel>"
  }
}
Einen neuen Schlüssel erzeugt man einmalig z. B. per PowerShell:
[Convert]::ToBase64String((1..32 | % { [byte](Get-Random -Max 256) }))

PRTG Monitoring

  • CPU/Memory: Warning bei 70-80%, Critical bei 85-90%
  • Disk: Warning bei 15-20% frei, Critical bei 5-10% frei
  • Passe Schwellwerte an die tatsächliche Last deines Systems an
  • Berücksichtige Lastspitzen (z.B. Batch-Jobs nachts)

NetScaler Health Checks

  • Intervalle: 15-30 Sekunden für kritische Services, 60-120 Sekunden für externe Services
  • Timeouts: 5-10 Sekunden für lokale Services, 10-15 Sekunden für externe APIs
  • Verwende HEAD statt GET wenn nur Erreichbarkeit geprüft werden soll
  • Bei externen APIs: Prüfe mehrere Statuscodeszahlen (z.B. [200, 201, 204])

Performance

  • Limitiere maxEntries auf das Notwendige (500-1000 reicht meist)
  • Vermeide zu kurze Intervalle bei vielen Health Checks
  • Nutze bodyContains nur wenn wirklich nötig (langsamer als Status-Code-Check)

Sicherheit

  • Verwende HTTPS für externe URLs (https://...)
  • Konfiguriere Encryption:ConnectionStringKey in appsettings.json, damit SQL Connection-Strings verschlüsselt gespeichert werden (enc:v1:…)
  • Der Master-Key darf nicht in config.json stehen — nur in appsettings.json oder per Umgebungsvariable Encryption__ConnectionStringKey
  • Limitiere Zugriff auf /admin/* Pfade über Firewall/Proxy

11. Troubleshooting

Service zeigt immer "Unhealthy"

Problem: Service ist laut HTML unhealthy, obwohl Metriken OK sind

Lösung:

  • Prüfe die Threshold-Werte in der config.json
  • Kontrolliere ob der Operator korrekt ist (">" für CPU/Memory, "<=" für Disk)
  • Schaue in die Logs: dotnet run zeigt die aktuellen Metrik-Werte

OK-Marker erscheint nicht

Problem: LoadBalancer oder PRTG findet den OK-Marker nicht

Lösung:

  • PRTG (/monitor/): OK-Marker erscheint nur bei Status: Healthy
  • NetScaler (/loadbalancer/): OK-Marker erscheint bei Healthy UND Degraded
  • Prüfe im Browser: Rechtsklick → "Seitenquelltext anzeigen" → Suche nach "Status:"
  • Teste mit: curl http://localhost:9090/admin/api-gateway/monitor/ | grep "Status:"
  • Bei Degraded/Warning: NetScaler-Pfad verwenden, wenn Server im Pool bleiben soll

NetScaler Health Check schlägt fehl

Problem: Health Check meldet immer Fehler

Lösung:

  • Teste die URL manuell: curl -v http://localhost:5067/health
  • Prüfe ob baseUrl korrekt ist (mit/ohne trailing slash)
  • Kontrolliere timeoutMs - ist er zu kurz?
  • Bei JSON-Path: Prüfe ob der JSON-Pfad korrekt ist (Case-Sensitive!)

Hohe CPU-Last durch SimpleAdmin

Problem: SimpleAdmin verbraucht viel CPU

Lösung:

  • Reduziere maxEntries in der History
  • Erhöhe die Intervalle bei Health Checks
  • Deaktiviere nicht benötigte Health Checks
  • Nutze HEAD statt GET bei Health Checks

JSON-Validierung funktioniert nicht

Problem: JSON-Path-Check schlägt fehl obwohl Wert korrekt ist

Lösung:

  • JSON-Pfade sind Case-Sensitive: $.Status ≠ $.status
  • Prüfe die JSON-Response manuell: curl http://localhost:5067/api/health | jq
  • Teste den JSON-Path online: jsonpath.com
  • Bei numerischen Werten: Verwende Number, nicht String ("value": 1000 statt "value": "1000")

Config-Änderungen werden nicht übernommen

Problem: Änderungen in config.json haben keine Wirkung

Lösung:

  • Stoppe und starte den SimpleAdmin neu
  • Prüfe auf JSON-Syntax-Fehler: cat config.json | jq
  • Kontrolliere Logs auf Fehler beim Laden der Config

12. Detailseite Features

Die Detailseite (<server>.<service>.html) zeigt umfassende Informationen zu einem Service an. Die Seite wird alle 60 Sekunden automatisch aktualisiert.

12.1 Metrik-Anzeige

Jede Metrik wird mit folgenden Informationen dargestellt:

  • Aktueller Wert: Der letzte gemessene Wert mit Einheit (z.B. "45.2%")
  • Durchschnittswert: Der Durchschnitt der letzten N Messungen (konfiguriert über minConsecutiveChecks)
  • Schwellwert: Die konfigurierten Warning/Critical-Schwellwerte mit Operator (z.B. "> 70% / > 85%")
  • Status: Farbcodiert (grün=OK, gelb=Warning, rot=Critical)
Durchschnittswert-Farbcodierung:
Der Durchschnittswert wird farblich gekennzeichnet basierend auf den Schwellwerten:
  • Grün: Durchschnitt liegt im OK-Bereich
  • Gelb: Durchschnitt liegt im Warning-Bereich
  • Rot: Durchschnitt liegt im Critical-Bereich

12.2 Logarithmische Verlaufsdarstellung

Die Verlaufshistorie wird als Balkendiagramm mit maximal 20 Balken dargestellt. Die Darstellung verwendet eine logarithmische Aggregation, um sowohl aktuelle als auch ältere Daten sinnvoll zu visualisieren.

Funktionsweise

Die letzten N Balken (N = minConsecutiveChecks, z.B. 5) zeigen die exakten Einzelwerte der letzten N Messungen. Dies entspricht den Werten, die für die Status-Bestimmung verwendet werden.
Die restlichen Balken (z.B. 15 bei maxBars=20) zeigen aggregierte Durchschnittswerte älterer Messungen. Je weiter links (älter), desto mehr Einzelwerte werden zu einem Balken zusammengefasst.

Beispiel bei 100 Verlaufseinträgen

Konfiguration: maxBars: 20, minConsecutiveChecks: 5

Balken 16-20 (rechts, neueste):
  Jeder Balken = 1 exakter Messwert (die letzten 5 Messungen)

Balken 1-15 (links, ältere):
  Logarithmische Verteilung der restlichen 95 Einträge:
  - Balken 1:  ~25 Einträge (älteste, aggregiert)
  - Balken 2:  ~18 Einträge
  - Balken 3:  ~13 Einträge
  - ...
  - Balken 15: ~2 Einträge (neueste der aggregierten Gruppe)

→ Je älter die Daten, desto mehr Werte werden zusammengefasst

Farbcodierung der Balken

Farbe Status Bedeutung
Grün OK Wert liegt unterhalb der Warning-Schwelle
Gelb Warning Wert liegt zwischen Warning- und Critical-Schwelle
Rot Critical Wert überschreitet die Critical-Schwelle

12.3 Legende

Unterhalb der Metriken befindet sich eine Legende, die folgende Informationen erklärt:

  • Status-Farben: Bedeutung der Farbcodes (OK, Warning, Critical)
  • Verlaufsbalken: Erklärung der logarithmischen Darstellung
  • Durchschnittswert: Basiert auf den letzten N Messungen
  • Status-Glättung: Hinweis auf die minConsecutiveChecks-Konfiguration

12.4 Auto-Refresh

Die Detailseite wird automatisch alle 60 Sekunden neu geladen. Dies wird über ein HTML-Meta-Tag gesteuert: 

<meta http-equiv="refresh" content="60">
Hinweis: Der Auto-Refresh zeigt immer die zuletzt generierten Daten an. Da SimpleAdmin als einmaliger Task läuft, werden die Daten nur aktualisiert, wenn SimpleAdmin erneut ausgeführt wird (z.B. per Cronjob).

13. E-Mail-Monitoring

Das E-Mail-Monitoring überwacht SMTP-Relay-Pfade durch zyklisch versendete Probe-E-Mails und prüft deren rechtzeitigen Eingang im Postfach. Dadurch werden Ausfälle im E-Mail-Zustellweg frühzeitig erkannt.

Globaler Feature-Toggle: features.emailMonitoring.enabled = true — muss aktiviert sein, damit die Sender- und Checker-Funktionen ausgeführt werden.
Konfigurierbar über WebUI → Einstellungen → Features → E-Mail-Monitoring.

13.1 Topologie

Das Monitoring basiert auf einer strikten Rollentrennung: Jede Instanz ist entweder Sender oder Checker — nie beides.

  • Sender-Instanzen (eine pro Netzwerksegment): Versenden Probe-E-Mails per SMTP an ein gemeinsames Monitoring-Postfach. Jede Probe testet einen eigenen SMTP-Relay-Pfad. Der Sendezeitpunkt wird in einer State-Datei festgehalten, sodass das konfigurierte Intervall eingehalten wird.
  • Checker-Instanz (eine, netzwerkweit): Verbindet sich per IMAP mit dem gemeinsamen Postfach und prüft für jeden konfigurierten Betreff-Filter, ob die neueste passende E-Mail innerhalb der Schwellwerte angekommen ist. 
Sender A (Segment 1) ──[SA-Probe] seg1──►
Sender B (Segment 2) ──[SA-Probe] seg2──►  Gemeinsames IMAP-Postfach
Sender C (Segment 3) ──[SA-Probe] seg3──►         │
                                                   │
                                         Checker-Instanz prüft:
                                         seg1: 8 Min → Healthy
                                         seg2: 45 Min → Warning
                                         seg3: nicht vorhanden → Critical

13.5 Passwort-Verschlüsselung

SMTP- und IMAP-Passwörter werden mit demselben AES-256-CBC-Mechanismus verschlüsselt wie SQL-Connection-Strings. Unverschlüsselte Werte werden beim Speichern über die WebUI automatisch verschlüsselt. 

# PowerShell: Schlüssel generieren
[Convert]::ToBase64String((1..32 | % { [byte](Get-Random -Max 256) }))

Der Schlüssel wird in appsettings.json unter Encryption:ConnectionStringKey konfiguriert und muss in Worker und WebUI identisch sein. Im Server-Editor stehen direkte Test-Buttons für SMTP und IMAP zur Verfügung (10 Sekunden Timeout).

14. Zentrale Benachrichtigungen (Notifier)

Eine SimpleAdmin-Instanz kann als zentraler Notifier betrieben werden: Sie aggregiert den Status aller Server über HTTP und verschickt eine Sammel-E-Mail, sobald ein noch nicht quittiertes Problem auftritt — jede Problemzeile enthält einen Direkt-Quittier-Link.

14.1 Aktivierung

Das Feature wird in der config.json unter features.notifications.enabled oder in der WebUI unter Einstellungen → Feature-Toggles → Benachrichtigungen aktiviert. Dort wählt man einen oder mehrere sendende Server (notifierServers) und eine zentrale WebUI (webUiServer). Ein Worker, dessen Hostname in notifierServers steht, übernimmt automatisch den Versand — kein --notify-Schalter mehr nötig. Alle URLs werden aus den baseUrls der Server abgeleitet.

14.2 Hochverfügbarkeit (zwei Instanzen)

Der Notifier kann auf zwei Servern parallel laufen, ohne dass eine Benachrichtigung doppelt versendet wird — und ohne zentrale Sperre oder Dateifreigabe. Jede Instanz veröffentlicht ihren Versand-Stand (notify-state.json) über IIS; vor dem Senden wird der Versand mit einem Zeitstempel „beansprucht" (claim-first), und jede Instanz liest den Stand der anderen (peerNotifyStateUrls). In Kombination mit versetzten Laufzeiten bleibt das Doppelversand-Risiko minimal, während ein verpasster Versand ausgeschlossen ist (fällt eine Instanz aus, übernimmt die andere automatisch).

Damit der Quittier-Link funktioniert, veröffentlicht die zentrale WebUI die aktiven Acknowledges nach wwwroot/status/acknowledges.json; der Notifier liest sie über acknowledgesUrl.

16. Datei-/Protokollüberwachung

Überwacht Fileshares auf hängengebliebene Dateien und durchsucht Logdateien nach Fehlersignaturen (z.B. die Verarbeitungsordner von Schnittstellen je Standort: Eingang / Kasse / Log). Ein zentraler Worker erreicht die Standort-Shares über UNC-Pfade; das Dienstkonto benötigt Leserechte. Funde laufen durch die normale Pipeline (Status, Probleme, Notifier-Mail) und tragen optional einen Wiki-Link sowie Nachbearbeitungsschritte.

16.1 Hängengebliebene Dateien

Eine Datei gilt je Verzeichnis als hängend, wenn sie älter als die Schwelle ist oder nach der Cutoff-Zeit (z.B. 21:45) noch vorhanden ist.

16.2 Log-Scans

Pro Logpfad (oder Glob wie …\log\*.log) werden Signaturen per regulärem Ausdruck gesucht; Treffer werden je Signatur gezählt. In der WebUI eine Signatur pro Zeile: Anzeigename :: Severity :: Regex.
